# DropMesh 1.3.0 跨平台 Windows 客户端设计

日期：2026-09-06  
目标版本：DropMesh 1.3.0  
状态：产品范围、架构、交互、安全和发布门禁已确认，等待书面规格审核

## 1. 背景与决定

DropMesh 1.2.6 是稳定的原生 macOS 文件传输应用，已经支持多台 Mac、六位码配对、
局域网与互联网传输、端到端加密、TURN 中继、文件夹、剪贴板、断点续传和应用内更新。
1.3.0 增加 Windows 客户端，使以下组合可以双向传输：

- Mac ↔ Mac；
- Mac ↔ Windows；
- Windows ↔ Windows。

选择“Rust 跨平台核心 + 原生系统外壳”路线。Windows 使用新的 Rust 核心和原生 Windows
界面；现有 Mac 传输核心在本版本不迁移、不替换、不链接 Rust 组件。Mac 只增加双语界面、
跨平台设备资料和必要的向后兼容适配。

保护现有 Mac 正常运行是首要发布门禁。Windows 功能没有通过完整跨版本验收时，不改变
Mac 1.2.6 的公开更新通道，也不向普通用户发布 1.3.0。

## 2. 产品目标、平台与边界

### 2.1 目标

普通用户在 Mac 或 Windows 上安装 DropMesh 后，无需账户、辅助网络软件、服务器地址或网络
知识，即可在五分钟内完成配对，并在同一局域网或不同网络之间发送文件。

Windows 首版与 Mac 核心能力对齐：

- 文件、多个文件和文件夹双向发送；
- 剪贴板内容发送；
- 自动接收和自定义接收目录；
- 传输速度、剩余时间、暂停、继续、取消；
- 断线恢复、断点续传和最终完整性校验；
- 接收通知、未读绿点、最近收到和历史记录；
- 设备重命名、移除、自动接收和单次大小限制；
- 应用内检查更新和升级；
- 简体中文与英文。

### 2.2 支持平台

- macOS 14 或更高版本，Intel x86_64 与 Apple arm64；
- Windows 10 22H2 与 Windows 11，x64；
- Windows ARM64 在后续小版本增加，不阻塞 1.3.0。

### 2.3 本版本不包含

- Linux、Android、iPhone 或 iPad 客户端；
- 用户账户、联系人、云盘或离线文件托管；
- 一次发送到多台设备；
- Microsoft Store 发布；
- 在 1.3.0 中把 Mac 的 Swift 传输核心迁移到 Rust；
- 改变现有传输帧版本、加密算法或 64 KiB 消息上限。

Linux 是后续目标。Rust 核心必须避免依赖 Windows UI，并通过平台适配接口访问密钥、通知、
目录和自动启动能力，使未来 Linux 客户端能够复用协议、网络、传输和存储模块。

## 3. 兼容性承诺

Windows 1.3.0 必须能够与 Mac 1.2.6 完成配对和双向传输。Mac 1.2.6 缺少平台图标和双语
界面，但不能因为不认识新增资料而拒绝 Windows 设备。

兼容规则：

1. 传输协议继续使用版本 1，二进制编码和字段顺序不变。
2. WebRTC 应用握手、身份验证、密钥派生和应用层加密不变。
3. 公网服务现有 HTTP/WSS 路由保持可用；新增字段只能是可选、可忽略的扩展。
4. 新客户端必须把缺少平台资料的既有设备安全地识别为 `unknown`，界面可根据已知客户端
   来源显示通用电脑图标，不以平台资料作为信任依据。
5. 新增平台资料必须由设备身份签名并通过独立的版本化信封传递。旧客户端不会解析该信封，
   但仍能使用原有在线状态、配对和信令消息。
6. 服务端只校验和转发受支持的信封；平台资料缺失、过期或无效时，设备仍可使用旧协议能力，
   但界面不得把未经验证的资料显示为可信信息。

## 4. 总体架构

### 4.1 仓库边界

现有目录继续承载 Mac 与服务端：

- `Sources/MacChannelCore`：稳定的 Swift Mac 核心；
- `App`：Mac AppKit/SwiftUI 外壳；
- `Services/rendezvous`：Go 公网协调服务；
- `Infrastructure`：生产部署；
- `Tests`：Mac 与服务端测试。

新增边界：

- `Protocol/`：跨语言规范、固定测试样本和兼容矩阵；
- `CoreRust/`：可复用 Rust 工作区；
- `Windows/DropMesh.App/`：WinUI 3 托盘应用；
- `Windows/DropMesh.Shell/`：资源管理器发送入口；
- `Windows/Packaging/`：MSIX、App Installer、签名与发布定义；
- `Tests/CrossPlatform/`：Swift↔Rust、Rust↔Go 和安装级验收工具。

Windows 项目不能改变 Mac 目标的链接依赖。Mac 的 SwiftPM 构建图不引用 `CoreRust` 或任何
Windows 产物；因此 Windows 核心的编译、运行或依赖失败不会影响 Mac 应用启动。

### 4.2 Rust 核心模块

Rust 工作区分为六个单一职责模块：

1. `dropmesh-protocol`：规范化 JSON、二进制传输帧、边界检查和固定测试样本。
2. `dropmesh-identity`：设备 ID、P-256 签名、信任记录、配对状态机和资料签名。
3. `dropmesh-network`：Bonjour/mDNS、在线状态、WSS 信令、ICE、STUN/TURN 和路线切换。
4. `dropmesh-transfer`：清单、分块、应用层加密、确认窗口、暂停、取消和断点恢复。
5. `dropmesh-storage`：SQLite 历史、临时文件、恢复记录、目录策略和原子完成。
6. `dropmesh-ffi`：面向 Windows 外壳的窄接口，只暴露命令、快照和事件，不暴露内部对象。

模块之间通过接口和不可变数据结构通信。Windows UI 不直接编码协议、读取数据库或持有私钥；
资源管理器扩展也不加载完整传输核心，只把经过验证的文件路径交给已运行的托盘进程。

### 4.3 Windows 外壳

Windows 外壳使用 C#、WinUI 3 和稳定版 Windows App SDK。初始实现固定到
Windows App SDK 2.4.0；升级框架版本需要先通过安装、托盘、通知、拖放和更新回归测试。
它通过窄 C ABI/PInvoke 边界调用 Rust 动态库。

窗口分为：

- 托盘菜单：最近收到、发送文件、发送剪贴板、传输与历史、配对设备、设置、退出；
- 悬浮投递区：接受资源管理器拖放，显示在线目标，松手发送；
- 设置页：本机名称、语言、接收目录、自动接收、登录启动、设备管理和更新；
- 传输页：进行中与历史、路线、速度、剩余时间和控制按钮；
- 配对页：显示或输入六位码，并处理允许、拒绝、超时和重试。

托盘进程单实例运行。第二次启动、资源管理器右键命令、通知点击和更新重启都通过受限的本机
进程间通道唤醒同一实例。通道只接受当前登录用户，限制消息大小和路径数量，并拒绝网络路径、
不存在路径和超出策略的请求。

### 4.4 Mac 变更边界

Mac 1.3.0 允许的改动只有：

- 把界面文本迁移到简体中文和英文资源；
- “Mac”专用文案改为“设备”，并显示 macOS、Windows 或通用电脑图标；
- 生成和验证可选的版本化设备资料；
- 显示远端版本、平台和能力；
- 为跨平台兼容新增固定样本与集成测试。

Mac 的发送、接收、连接回退、分块、加密、历史数据库和更新器实现不做重写。若平台资料扩展
需要触碰现有信任或传输代码，必须放在适配层并证明关闭扩展后行为与 1.2.6 一致。

## 5. 协议与安全

### 5.1 身份和密钥

- 设备 ID 继续取 P-256 签名公钥原始表示的 SHA-256 前 16 字节。
- 签名继续使用 ECDSA P-256/SHA-256 和 DER 表示。
- WebRTC 应用握手继续使用临时 P-256 密钥协商、双方签名 transcript 和 HKDF-SHA256。
- 文件继续在 WebRTC 之上使用应用层派生密钥加密；TURN 和服务端只能看到密文。

Windows 长期私钥由 Windows CNG 创建为当前用户的不可导出密钥。Rust 身份模块通过平台
适配器请求签名，不能读取私钥字节。公钥转换为与 CryptoKit `rawRepresentation` 一致的
65 字节未压缩点；Windows 返回的 ECDSA `r || s` 由适配器规范化为最短 DER 后进入现有协议。
临时协商密钥只存在于进程内存，任务结束后释放。

### 5.2 设备资料扩展

`DeviceProfileV1` 是独立签名信封，至少包含：

- `deviceID`；
- `platform`：`macOS`、`windows` 或 `unknown`；
- 语义化客户端版本与整数构建号；
- UI 语言：`zh-Hans`、`en` 或 `unknown`；
- 排序且受上限约束的能力标识；
- 签发时间、到期时间和随机 nonce；
- 设备身份签名。

能力标识只用于渐进增强，例如文件夹、剪贴板、资料版本和未来协议版本。它不能降低身份验证、
绕过接收策略或让未配对设备成为发送目标。服务端不基于平台或语言决定信任。

### 5.3 WebRTC 技术门禁

Windows 核心初始使用 `webrtc-rs` 0.21.0，由 `Cargo.lock` 固定发布包校验和，不跟随分支。
该依赖仍为 1.0 前版本，因此在继续完整客户端开发前必须完成一个可废弃的技术门禁：

- Windows x64 构建和干净环境加载；
- 与当前 Mac WebRTC M150 建立可靠、有序数据通道；
- host、server-reflexive 和 relay ICE 路线；
- 64 KiB 上限、背压、取消、超时和关闭；
- 双方应用握手与 exporter 派生结果一致；
- 连续 10 GiB 双向流量无静默丢帧或乱序。

任何一项失败都停止采用该库并回到书面设计评审，不允许在实现中静默更换 WebRTC 栈或降低
安全、恢复、顺序和内存边界。

## 6. 用户体验

### 6.1 安装与启动

Windows 从官网或 GitHub Release 下载经过代码签名的 MSIX/App Installer。安装按当前用户
进行，不要求管理员权限。首次启动显示最小欢迎页，说明托盘位置、接收目录和通知；不要求
配置网络或创建账户。

Mac 和 Windows 都自动跟随系统语言，并允许在设置中选择“跟随系统”“简体中文”或“English”。
设备名称默认使用系统计算机名称，但只在配对界面和已建立信任的设备间显示。

### 6.2 配对与设备

任意已配对设备都可以显示六位码，另一台 Mac 或 Windows 输入后，由已有设备点一次“允许”。
配对码五分钟有效且只能使用一次。主机未批准、双方 transcript 未验证、双向信任未提交前，
设备不能出现在可发送目标中。

设备列表统一称为“已配对设备”，显示系统图标、名称、在线状态和最后验证的客户端版本。
移除设备后立即撤销本机信任并传播签名撤销事件；旧缓存不得继续显示为已配对或可发送。

### 6.3 Windows 发送入口

采用 A+B 组合：

1. **资源管理器右键发送：** 选中文件或文件夹后选择“用 DropMesh 发送”，二级菜单或轻量
   选择器只显示已配对且在线的设备。
2. **托盘悬浮投递区：** 点击托盘图标后可以打开小型投递区；把一个或多个文件、文件夹拖入，
   再拖向或点击目标设备发送。连续操作期间投递区可以固定，默认发送后关闭。

两种入口共用同一准备、策略检查、目标快照和发送命令。放手或确认瞬间会重新验证设备仍在线；
失效时不创建失败的历史任务，而是提示“设备刚刚离线，请稍后重试”。

托盘菜单还提供“发送文件”和“发送剪贴板”。剪贴板文本写入受控临时 UTF-8 文件，图片使用
无损 PNG，复制的文件或文件夹直接使用源路径；不支持的格式给出明确提示。临时文件在完成、
取消或失败后清理。

### 6.4 接收与最近文件

默认目录为用户的 `Downloads/DropMesh`。用户可以选择全局目录，也可以为某个来源设备选择
专用目录。Windows 使用系统授权和受控句柄；Mac 继续使用安全作用域书签。

内容先写入应用私有临时区。只有分块验证、整体 SHA-256 和目标策略都通过后，才原子移动到
最终目录。同名文件自动编号，不覆盖现有内容。

完成后发送本地系统通知并在托盘图标显示绿色圆点。点击通知或托盘第一层的“最近收到”直接
在资源管理器或 Finder 中定位文件。用户查看最近收到列表后清除绿点，不要求进入历史页。

### 6.5 在线状态与路线

设备目录合并本地 mDNS 和已认证公网在线证据。WebSocket 使用应用级往返 ping、明确超时、
系统唤醒/网络恢复重连和带抖动退避，不能把单个过期计时器当作离线结论。

每次传输按以下顺序自动尝试：

1. 局域网直连；
2. 互联网点对点直连；
3. 端到端加密 TURN 中继。

路线切换保持同一 TransferID 和已确认分块。普通用户不选择路线，只在详情中看到“直接连接”
或“安全中继”。目标离线时不把文件上传到服务端，也不提供云端稍后投递。

## 7. 错误处理与恢复

所有错误映射为稳定类别和面向用户的下一步：

- 目标离线：保留源文件，提供“重试”；
- 服务暂时不可用：继续本地发现并自动重连；
- 直连失败：自动切换中继，不要求用户操作；
- 网络中断：保留已确认范围，恢复后继续；
- 目录权限失效：暂停接收并提供“重新选择目录”；
- 磁盘不足：拒绝最终写入，保留可恢复状态并显示所需空间；
- 文件在发送前被移动或修改：不发送旧清单，要求重新选择；
- 版本或能力不兼容：指出需要升级哪台设备；
- 协议、签名或摘要无效：立即关闭该连接，不自动降级安全检查；
- Rust 核心异常：终止受影响任务并由托盘进程重新建立核心，其他历史和源文件保持完整。

崩溃恢复只信任经过认证的恢复记录和已落盘分块。未完成内容不使用最终名称；取消会清理临时
内容和密钥，但保留最小历史结果。日志不得包含文件名、完整路径、配对码、私钥、会话密钥、
清单明文或原始网络载荷。

## 8. 本地化

Mac 和 Windows 使用同一稳定消息键和术语表，但各自使用原生本地化资源。所有用户可见文本、
通知、菜单、错误、安装说明、更新说明和辅助功能名称必须覆盖简体中文与英文。

本地化门禁包括：

- 不允许源代码散落未登记的用户可见字符串；
- 中英文截图覆盖托盘、悬浮投递区、配对、设置、传输和错误状态；
- Windows 100%、125%、150% 和 200% 缩放；
- 长英文设备名、中文文件名、emoji、组合字符和从右向左文件名不破坏布局或路径安全；
- 切换语言不重启传输核心，不中断活动任务。

## 9. 打包、更新与发布

### 9.1 Windows

- 使用自包含、x64、按用户安装的签名 MSIX；
- App Installer 文件通过 HTTPS 发布，启动时检查更新且不在活动传输中强制重启；
- 包具有固定 Publisher、Package Family Name 和升级身份；
- 资源管理器入口、通知、登录启动和协议唤醒均声明在包清单中；
- 正式包必须通过签名链、时间戳、SmartScreen/Defender 和干净环境安装检查；
- 卸载默认删除程序文件，保留接收文件、本机身份、信任和历史，重新安装后可以恢复；设置页
  提供“清除本机身份与记录”，执行前明确说明该设备将需要重新配对。

Microsoft Store 不属于 1.3.0。用户从网站下载 `.appinstaller` 或 `.msixbundle` 后手动打开；
不依赖可能被系统策略禁用的网页协议直接唤起安装。

### 9.2 Mac

Mac 继续发布 Apple Developer ID 签名、公证、装订的 DMG，并使用现有 Sparkle feed。Windows
清单、证书或 CDN 失败不能覆盖 Mac feed。Mac 1.3.0 只有在 Windows 候选通过全部门禁后才
进入现有更新通道。

Mac 和 Windows 对外都显示版本 1.3.0，但使用独立、单调递增的构建号和平台安装资产。发布
清单记录提交、平台、架构、版本、构建号、签名主体、SHA-256 和验收证据。

## 10. 验证矩阵

### 10.1 自动化

每次合并必须运行：

- 现有 Swift 完整测试和 Mac 本地发布契约；
- Go 单元、race、vet 和服务端契约；
- Rust 单元、属性、模糊、并发、资源上限和恢复测试；
- Swift↔Rust 固定样本：规范化 JSON、P-256 公钥、DER 签名、DeviceID、transcript、HKDF、
  应用层密文、传输帧、清单和 ResumeMap；
- Rust↔Go 认证、在线状态、配对、信令、TURN 凭据和无效请求测试；
- Windows x64 构建、MSIX 安装、启动、升级和卸载自动化；
- 中英文资源完整性和禁止遗留 Mac 专用用户文案检查。

### 10.2 真实系统验收

正式发布前必须在真实安装候选上完成：

- Mac 1.2.6 ↔ Windows 1.3.0 双向；
- Mac 1.3.0 ↔ Windows 1.3.0 双向；
- Windows 10 22H2 ↔ Windows 11 双向；
- macOS Intel 与 Apple 芯片回归；
- 同一局域网、不同公网直连和强制 TURN；
- 文件、多个文件、文件夹、剪贴板、空文件和大文件；
- 中文、英文、emoji、组合字符、长路径和同名冲突；
- 暂停、继续、取消、断网、系统睡眠、进程重启和电脑重启；
- 目录权限丢失、磁盘不足、源文件修改、对端拒绝和设备撤销；
- Windows 干净安装、覆盖升级、后台更新、登录启动、通知点击、托盘恢复和资源管理器入口；
- Mac 现有拖到菜单栏图标发送、配对、通知、绿点、最近收到和 Sparkle 更新无退化。

每行证据记录候选提交、应用版本/构建、操作系统版本、设备架构、路线、方向、源/目标 SHA-256、
断点位置、最终路径、耗时和结果。自动化、单机模拟或未签名包不能替代真实跨系统验收。

## 11. 实施顺序与停止条件

1. 抽取现有协议规范和 Swift 固定样本，不改变运行行为。
2. 完成 Rust 协议、身份和 WebRTC 技术门禁。
3. 完成无界面的 Rust↔Mac↔Go 双向传输工具和恢复测试。
4. 完成 Windows 托盘应用、配对、发送、接收和历史。
5. 完成资源管理器入口、悬浮投递区、通知、本地化和设置。
6. 增加 Mac 双语和平台资料适配，并运行完整回归。
7. 完成 MSIX/App Installer、Windows 签名、Mac 公证和真实系统验收。
8. 先发布候选版；全部证据通过后，同日发布 Mac 与 Windows 1.3.0 正式版。

停止条件：

- Rust WebRTC 无法满足可靠、有序、TURN、背压或长流量门禁；
- Swift↔Rust 任一密码学或字节级样本不一致；
- 必须改变协议版本 1 才能完成基本互传；
- Windows 安装需要用户关闭系统安全或手工安装运行库；
- Mac 1.2.6 兼容性或 Mac 现有功能回归失败；
- 正式 Windows 代码签名、Mac 签名公证或真实设备证据缺失。

触发停止条件时，候选只能作为内部测试版，不得向普通用户发布，也不得通过现有 Mac 更新通道
推送。

## 12. 成功标准

一个没有网络技术背景的用户能在受支持的 Mac 或 Windows 上完成安装，用六位码与现有设备
配对，从 Finder、资源管理器右键、Windows 悬浮投递区或剪贴板发起传输，并在目标下载目录
收到经过完整性校验的内容。整个过程不需要账户、服务器配置、辅助网络软件或管理员权限。

同时，仍运行 Mac 1.2.6 的用户可以继续正常配对和传输；现有 Mac 功能、性能、安全、更新和
本地数据没有因为 Windows 开发发生退化。
