# DropMesh 品牌与接收提醒设计

日期：2026-09-02  
状态：用户已批准方向，待书面规格确认  
目标平台：macOS 14 或更高版本；品牌与产品命名面向未来的 Windows 客户端

## 1. 目标

将当前对外名称从 MacChannel / Mac 通道迁移为跨平台品牌 **DropMesh**，补齐正式应用图标，并让后台接收文件后的结果清楚可见。菜单栏界面应符合用户对原生临时面板的预期：打开后点击其他位置即可自动关闭，不影响后台传输。

成功标准：

1. Finder、应用程序目录、系统通知和安装镜像均显示 DropMesh 品牌，不再出现默认空白应用图标。
2. 文件只有在完整接收并成功保存后才产生一次系统通知和菜单栏绿色未读点。
3. 用户打开菜单栏主界面后，绿色未读点立即清除。
4. 用户点击 DropMesh 界面以外的区域时，当前菜单栏弹窗自动关闭；正在进行的传输继续在后台运行。
5. 从现有 MacChannel 正式版本覆盖升级后，设备身份、钥匙串、配对关系、设置、历史和接收目录全部保留。

## 2. 品牌方案

### 2.1 名称

对外产品名采用 **DropMesh**：`Drop` 表达拖放和快速发送，`Mesh` 表达多设备互联。名称不绑定 macOS，后续 Windows、Linux 或移动端可继续使用同一品牌。

本次属于对外品牌迁移，不迁移持久化身份。以下内部标识继续保留：

- Bundle ID `com.mason.macchannel`
- 代码签名 Team ID 与 designated requirement
- 钥匙串 service/account 标识
- UserDefaults、数据库、日志和应用支持目录
- GitHub 仓库和现有 Sparkle feed URL
- Swift module、可执行文件及内部类型名（除非展示给用户）

保留这些标识可以让旧版原地升级，不产生一套新的设备身份或空白配对列表。内部重命名不带来用户价值，且会扩大迁移风险，因此不在本次范围内。

### 2.2 应用图标

图标使用独立于 Telegram 和 AirDrop 的几何语言：

- 石墨黑圆角方形背景。
- 中央是暖白色文件块。
- 文件块两侧由两个荧光绿色节点和一条连接路径组成，表达“文件在设备网格中移动”。
- 不使用纸飞机、蓝色圆底、无线电同心圆或系统默认模板网格。
- 不放文字、首字母或细小装饰；16px 尺寸仍能辨认文件块与两个连接点。

颜色基准为石墨黑 `#1D1F23`、暖白 `#F5F2EA`、连接绿 `#45E07C`。最终资产生成完整 `.icns` 尺寸组，至少覆盖 16、32、128、256、512 和 1024 像素，并在构建时写入 `CFBundleIconFile`。源资产保存在仓库，构建脚本不得依赖开发机上未提交的图标文件。

菜单栏图标保持适配 macOS 明暗菜单栏的模板图像，不直接复用彩色应用图标。品牌形状可以调整为简化的“文件与两个节点”，但普通、拖入就绪和传输中的状态必须保持现有可辨识度。

### 2.3 对外显示与升级兼容

应用的 `CFBundleName` 和 `CFBundleDisplayName` 显示 DropMesh。DMG 卷名、安装说明、菜单标题、退出命令、设置页版本行、通知来源和发布说明统一使用 DropMesh。

为降低 Sparkle 原地更新时改变应用包路径的风险，本次过渡版本保留磁盘上的旧 bundle 文件名与可执行文件名；Finder 通过 Bundle 展示名称显示 DropMesh。公开安装镜像文件可命名为 `DropMesh.dmg`，更新 feed 指向新资产。发布验收必须分别覆盖旧版原地升级和全新拖入安装。

## 3. 接收完成通知

### 3.1 触发规则

通知由实时接收控制器的成功完成事件触发，而不是由历史列表变化触发。只有同时满足以下条件才发送：

1. 传输通过认证和完整性校验。
2. 所有本次接收项目已成功写入用户配置的接收目录。
3. 接收结果不是取消、失败或空结果。

每个成功的接收批次只发送一次通知。应用重启后加载历史、接收监听器重启、配对刷新或设置刷新不得重复通知。通知服务的失败不能改变传输结果，也不能阻止历史写入。

### 3.2 权限与内容

应用首次启动包含此功能的版本时，使用 macOS 原生通知授权弹窗申请 `alert` 和 `sound` 权限。用户拒绝后不反复弹出；菜单栏绿色未读点仍正常工作。设置页显示当前通知状态，并在权限被拒绝时提供“打开系统设置”的入口，不提供伪装成已开启的应用内开关。

通知标题为“已收到新文件”。单文件时正文显示文件名，多文件时显示“已收到 N 个文件”，并显示已保存到用户选择的接收位置。不得在日志中记录通知正文或完整文件路径。

点击通知后在 Finder 中显示接收结果：单文件选择该文件，多文件打开接收目录。文件已被移动或删除时退回到打开接收目录；无法打开 Finder 时静默保留传输成功状态。

### 3.3 服务边界

新增一个主线程拥有的接收提醒服务，封装 `UNUserNotificationCenter`、授权状态、通知发布和通知点击处理。生产环境使用系统实现；测试使用内存实现记录请求，不调用真实通知中心。

生产运行时在成功接收后先持久化历史，再把不可变的接收摘要交给提醒服务。提醒服务随后：

1. 标记菜单栏存在未读接收。
2. 在已授权时发布系统通知。
3. 保存通知标识到目标 URL 的短期内存映射，以响应用户点击。

任何一步失败都不能回滚已保存的文件或历史。

## 4. 菜单栏绿色未读点

菜单栏控制器增加一个独立的布尔状态 `hasUnreadReceive`。成功接收时设为 `true`；用户点击菜单栏图标、打开主菜单时立即设为 `false`。关闭菜单或弹窗不会重新点亮，下一次成功接收才会再次出现。

绿色点使用独立覆盖视图绘制在菜单栏图标右上角，直径约 6pt，使用 `NSColor.systemGreen`。不能把整个菜单栏图标改为非模板图片，否则深色菜单栏下会再次出现黑色不可见问题。覆盖视图不接收鼠标事件，不缩小原有点击区域。

VoiceOver 在存在未读时把菜单栏按钮描述扩展为“DropMesh，有新接收文件”；清除后恢复为“DropMesh”。颜色不是唯一提示渠道。

多次接收只维持一个未读点，不显示数字角标。本次不持久化未读状态；应用重启代表新的使用会话，历史页仍保留接收记录。

## 5. 菜单栏弹窗关闭行为

所有从菜单栏打开的传输、配对和设置 `NSPopover` 使用 `.transient` 行为。用户点击其他应用、桌面或 DropMesh 面板外部区域时，当前弹窗立即关闭。

关闭只影响界面：

- 不取消发送或接收任务。
- 不停止安全服务、设备发现或更新下载。
- 再次打开传输界面时从同一状态源恢复实时进度。
- 拖放目标选择面板继续服从拖放生命周期，不能因普通弹窗策略变化提前吞掉正在进行的 drop。

用户主动点击关闭按钮、再次点击菜单栏图标或打开另一个 DropMesh 界面时仍只保留一个活动弹窗。弹窗关闭后恢复菜单栏按钮的键盘与 VoiceOver 焦点。

## 6. 数据流

成功接收的数据流如下：

1. 连接监听器交给接收控制器一个已认证通道。
2. 接收控制器校验并写入接收目录，形成成功结果。
3. 历史存储先记录成功结果。
4. 应用级接收事件分发器把接收摘要发送给提醒服务和菜单栏控制器。
5. 菜单栏显示未读点；系统通知在权限允许时发布。
6. 用户打开菜单栏界面，菜单栏控制器清除未读点。
7. 用户点击通知，提醒服务在 Finder 中显示文件或接收目录。

界面控制器不读取数据库来推断“新文件”，避免历史重放产生重复提醒。通知服务不拥有传输协调器，也不能改变传输状态。

## 7. 错误处理

- 通知权限未决定：申请一次授权；本次若来不及显示系统通知，仍显示菜单栏未读点。
- 通知权限被拒绝：不报传输错误，不重复申请，设置页提供系统设置入口。
- 通知中心发布失败：保留未读点和历史，只记录不含用户内容的稳定错误类别。
- Finder 目标不存在：打开当前接收目录；目录也不可用时不弹出误导性错误。
- 图标资源缺失或尺寸不完整：正式构建必须失败，不能退回默认占位图。
- 品牌迁移后找不到旧数据：升级验收直接失败，禁止发布。
- 弹窗关闭时仍有传输：界面关闭但任务继续，重新打开后进度必须连续。

## 8. 测试与验收

### 8.1 自动化测试

按测试驱动方式逐项先看到失败，再实现：

1. 成功接收产生一次提醒事件；失败、取消、空结果和历史恢复不产生提醒。
2. 提醒服务在授权、拒绝和发布失败时保持正确降级行为。
3. 单文件与多文件通知内容正确，点击动作选择文件或打开目录。
4. 菜单栏未读点从关闭到开启，再在打开菜单时清除；连续接收不产生多个覆盖视图。
5. 未读和普通状态都有正确的 VoiceOver 描述。
6. 所有普通 `NSPopover` 的行为为 `.transient`，关闭界面不调用传输取消。
7. 构建产物包含 `CFBundleIconFile`、有效 `.icns` 和 DropMesh 展示名称。
8. 旧内部标识、生产签名锚和 Sparkle 更新配置保持不变。

### 8.2 安装版验收

发布前必须使用正式签名、公证、装订票据的安装包完成：

1. 在干净测试位置安装，确认 Finder 和应用程序目录显示 DropMesh 及新图标，16px 到 1024px 无默认占位或模糊边缘。
2. 从当前公开 MacChannel 版本原地升级，确认显示名和图标更新，同时原设备身份、配对、设置、历史和接收目录保持一致。
3. 两台真实 Mac 各完成一次局域网直连和一次加密中继接收；成功后接收端出现通知与绿点，发送端不出现接收通知。
4. 点击通知能在 Finder 定位文件；点击菜单栏图标清除绿点。
5. 打开传输、配对和设置界面，分别点击桌面及其他应用，确认弹窗自动关闭。
6. 在传输中关闭界面再重新打开，确认进度连续且最终 SHA-256 与源文件一致。
7. 通知权限拒绝状态下重复步骤 3，确认文件仍成功、绿点仍出现且不显示虚假报错。
8. 重新运行完整 Swift 测试、真实 rendezvous/STUN/TURN、强制中继、大文件和 Sparkle 安全更新矩阵。

只有自动化测试、两机真实接收和公开下载产物回验全部通过后，才能发布该版本。

## 9. 本次范围外

- Windows 客户端实现；本次只保证品牌和数据模型不阻塞 Windows 版本。
- 内部 Bundle ID、代码模块、钥匙串或数据目录迁移。
- 数字未读角标、通知中心历史管理或跨设备已读同步。
- 传输完成声音的自定义音效。
- 商标注册或法律意见；DropMesh 上线前仍需正式商标与应用商店名称审查。
