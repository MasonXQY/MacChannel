# Mac 通道内置公网通道与傻瓜化体验设计

日期：2026-08-30
目标版本：v1.1.0
状态：架构、交互和验收标准已确认，待书面规格审核

## 1. 背景与决定

当前 v1.0.1 同时暴露“个人网络”和“公共服务”两种连接模式。个人网络依赖用户自行安装、
登录并配置 Tailscale，设置页还暴露连接模式、服务地址、启用状态和重启提示。这个方案虽然
可以在没有官方基础设施时工作，但不符合“安装后直接使用”的产品目标，也造成了第二台 Mac
启动后不知道下一步该做什么的问题。

v1.1.0 改为只提供应用内置公网通道：

- 不安装、不检测、不调用 Tailscale，也不要求用户拥有相关账户。
- 不让普通用户选择连接模式或填写服务器地址。
- 应用启动后自动连接官方协调服务，同时保留 Bonjour 局域网发现。
- 连接顺序固定为局域网直连、互联网点对点直连、端到端加密 TURN 中继。
- 首次配对只要求六位码和旧 Mac 上的一次“允许”。
- 服务端不保存文件，不提供离线投递，也不能解密文件内容。

本设计取代
`2026-08-27-personal-mesh-install-design.md` 作为 v1.1.0 及后续版本的产品方向。旧设计保留为
历史记录，不能再作为默认运行方式或发布验收依据。原始
`2026-08-26-mac-channel-design.md` 中的端到端加密、断点续传、多设备、菜单栏拖放和
LAN → Internet → TURN 路由目标继续有效；本文覆盖其指纹确认和设置入口。

## 2. 产品目标与边界

### 2.1 目标

用户在两台或多台 macOS 14+ Mac 上安装同一个公证应用后，无需安装辅助软件、注册账户、
理解网络术语或修改系统网络设置，即可完成配对和跨网络文件传输。

成功标准是：一个不懂 Tailscale、WebRTC、STUN 或 TURN 的用户，只根据界面上的中文提示，
可以在五分钟内让第二台 Mac 出现在第一台 Mac 的发送目标中。

### 2.2 本版本包含

- 两台及多台 Mac 的长期信任、设备列表、重命名和移除。
- 六位一次性配对码，旧 Mac 单侧明确批准。
- 同一局域网和不同互联网网络之间的在线传输。
- 文件、多个文件和文件夹的菜单栏拖放发送。
- 自动接收、可选择接收目录、同名文件安全编号。
- 断线自动重连、断点续传和最终内容完整性校验。
- 官方协调服务、短期 TURN 凭据、运行监控和安全限流。
- 从 v1.0.1 保留本地身份、信任、设置、历史和未完成任务的升级迁移。

### 2.3 本版本不包含

- 用户账户、第三方登录或联系人系统。
- 对方离线时把文件暂存在云端。
- 服务端文件存储、网页下载链接或历史同步。
- 一次发送到多台设备。
- iPhone、iPad、Windows、Android 或 Linux 客户端。
- 用户自建服务器入口。开发和企业调试可通过仅开发构建使用覆盖配置，但公开 Release 不显示。

## 3. 最终用户体验

### 3.1 安装与启动

应用继续以 Developer ID 签名、公证并装订的 `MacChannel.dmg` 分发。用户把应用拖入
“应用程序”后启动，应用只在菜单栏常驻，不弹出网络配置向导。

首次启动自动完成：

1. 从钥匙串读取或创建本机设备身份。
2. 打开本地数据库和默认接收目录 `~/Downloads/Mac 通道`。
3. 启动 Bonjour 发现并连接内置的官方协调服务。
4. 恢复已配对设备的在线状态。

未配对任何设备时，菜单主行动项是“添加另一台 Mac”。服务连接失败不阻塞应用启动；
同一局域网能力和本地设置仍可使用。

### 3.2 首次配对

旧 Mac：

1. 点击“添加另一台 Mac”。
2. 选择“在这台 Mac 上显示配对码”。
3. 界面显示六位数字、剩余有效时间和“请在另一台 Mac 输入”。
4. 收到加入请求后显示“允许‘某某的 Mac’加入吗？”，提供“允许”和“拒绝”。

新 Mac：

1. 点击“添加另一台 Mac”。
2. 选择“输入配对码”，输入六位数字。
3. 显示“正在等待旧 Mac 允许”。
4. 旧 Mac 允许并完成双向授权后显示“已连接”。

配对码五分钟有效、只能成功使用一次。取消、拒绝、超时或握手失败会烧毁当前会话。普通
界面不再显示密钥指纹，也不要求用户在两台设备上分别确认。

### 3.3 多 Mac

任意已信任 Mac 都可以批准新 Mac。批准者为新设备签发带签名的成员授权，并把新成员事件
同步给当前可信设备；新 Mac 同时获得现有成员的已验证设备密钥。同步完成后，新 Mac 与既有
Mac 互相出现在设备列表中，无需逐台重复配对。

成员事件只能由已经可信的设备签名，服务只保存和转发不可伪造的授权或撤销信封。设备暂时
离线时，在下次上线后补齐成员事件；缺失或冲突事件保持“正在同步”，不能提前用于传输。

### 3.4 拖放发送

1. 用户从 Finder 拖起一个或多个文件或文件夹。
2. 拖入菜单栏纸飞机图标后，图标切换为明确的 Ready 状态。
3. 图标下方展开当前在线且可接收的可信 Mac。
4. 拖到目标 Mac 时目标放大并显示“松开发送”。
5. 松手立即开始，不再弹确认框。

离线设备在普通菜单的设备列表中显示为灰色，但不进入拖放目标扇。放手瞬间状态失效时，
源文件不受影响，并提示“这台 Mac 刚刚离线，请稍后再试”。

### 3.5 接收与完成

可信设备默认自动接收，默认目录为 `~/Downloads/Mac 通道`。文件先写入应用管理的临时目录，
只有完整性校验通过后才原子移动到最终位置。同名内容自动追加序号，绝不覆盖已有文件。

完成后发送系统通知；点击通知或历史项目可以在 Finder 中显示结果。接收目录可以改为用户
选择的其他目录，安全作用域书签必须跨重启恢复。

### 3.6 设置精简

普通设置只保留：

- 本机显示名称。
- 已配对 Mac（在线状态、重命名、移除）。
- 接收目录。
- 自动接收开关。
- 登录时启动。

以下项目从普通设置完全删除：

- 个人网络/公共服务模式。
- Tailscale 安装、登录、Serve 和连接状态。
- 协调服务 URL。
- “启用个人网络通道”。
- 因网络模式变更而要求重启的提示。

“高级诊断”作为折叠入口，只显示可复制的应用版本、服务状态、匿名错误类别和最近连接路线；
不允许编辑生产端点，也不显示文件名、完整路径、密钥、配对码或原始网络日志。

## 4. 客户端架构

### 4.1 单一运行模式

`ProductionAppRuntime` 在 Release 构建中只装配公共服务路径。生产协调端点和受支持的 STUN
配置写入签名应用资源，TURN 凭据只由协调服务按短期授权下发。开发测试可以通过依赖注入或
测试资源覆盖端点，但用户设置不能覆盖它。

启动流程不得因为远端服务失败而抛出整个应用初始化错误。远端能力使用明确状态机：
`connecting`、`online`、`degraded`、`offline`。重试采用带抖动的指数退避，网络恢复和系统
唤醒会触发立即重连，但只能存在一个活跃重连任务。

### 4.2 设备目录

`DeviceDirectory` 继续合并两类证据：

- Bonjour 发现的局域网可达性。
- 官方协调服务返回的已认证在线状态。

设备只有在 `TrustRepository` 中拥有当前有效密钥，并且可达性证据与同一 DeviceID 的签名
挑战一致时，才可成为发送目标。局域网发现不能把陌生设备自动变为可信设备。

### 4.3 连接路径

每个传输任务保持稳定 TransferID，并按顺序尝试：

1. **局域网直连：** Bonjour 已解析目标时优先建立认证 WebRTC 通道。
2. **互联网直连：** 通过协调服务交换信令和 ICE 候选，尝试 NAT 穿透。
3. **加密中继：** 直连在规定窗口失败后自动使用 TURN relay 候选。

三条路径使用同一可信设备身份和应用层端到端加密协议。路线切换不创建新的用户任务，已确认
分块继续有效。界面只在传输详情或高级诊断中显示“直接连接”或“安全中继”，不要求用户选择。

### 4.4 配对状态机调整

现有 `PairingCoordinator` 的临时 P-256 ECDH、双方长期身份签名、transcript 绑定、channel
tag 和双向授权提交继续使用。UI 和状态机改为：

- 主机：`displayingCode → approvalRequested → committing → confirmed`。
- 加入方：`joining → awaitingHostApproval → committing → confirmed`。
- 任一方：失败、拒绝、取消或超时后回到可重试状态。

旧 Mac 的“允许”替代双方人工 `confirmFingerprint`。主机未批准前，双方都不得把信任记录写入
持久存储；加入方只有收到主机签名、且与本次加密 transcript 绑定的授权信封后才能提交。
服务不能自行生成有效的设备签名。

六位码会被官方服务看到，因此本设计明确采用以下威胁边界：TLS 防止普通网络攻击者窃听或
篡改；服务端执行按码、来源和全局限流；设备签名保护已建立的长期信任和后续传输；但首次
配对不通过跨设备指纹比较抵抗“官方协调服务本身主动冒充”的极端场景。服务仍然无法读取后续
文件内容。若未来要求连官方配对服务也完全不可信，需增加二维码或双端图案比较，这不属于
v1.1.0。

### 4.5 多设备信任同步

在现有双向 `SignedTrustRecord` 之上增加有序的成员事件信封，至少包含 group ID、事件 ID、
签发设备、目标设备、目标长期公钥、动作、父事件摘要、时间和签名。客户端规则为：

- 只有当前可信且未撤销的签发设备能添加新成员。
- 新成员必须提供本次配对 transcript 中使用的同一长期公钥。
- 同一设备 ID 绑定不同公钥视为冲突，保持不可用并显示修复提示。
- 重复事件幂等；乱序事件先隔离，补齐父事件后再应用。
- 移除设备会使其立即失去本机连接资格，并向其他成员传播签名撤销事件。
- 被移除设备不能用旧成员事件重新获得信任，必须重新走六位码配对并产生新事件。

服务端只保存签名信封和最小投递游标，不决定谁可信。客户端在应用成员事件前始终自行验证
签名、父关系、当前撤销状态和资源上限。

### 4.6 v1.0.1 升级迁移

升级不得轮换钥匙串中的设备身份，也不得删除信任、接收目录、历史、数据库、staging 或恢复
journal。迁移过程：

1. 读取旧设置，保留显示名称、目录、自动接收和登录启动。
2. 忽略并停止写入 `connectivityMode`、`personalMeshEnabled` 和用户 `rendezvousURL`。
3. 不再初始化 Tailscale 命令客户端、Serve 配置器、mesh listener 或 mesh peer refresh。
4. 现有直接信任记录继续有效，并在可信设备首次同时在线时转换为幂等成员事件。
5. 旧的个人网络传输任务保留 TransferID 和 ResumeMap，用公共连接路径恢复；不能从零重传
   已经确认的分块。
6. 迁移成功后才写入新 schema 版本；失败时保持旧数据可恢复，不做破坏性回滚。

Tailscale 相关源码可在公共路径和迁移测试稳定后删除；删除时必须证明 Release 二进制不再包含
CLI 路径、下载链接或 Serve 调用。已经安装的 Tailscale 应用属于用户，不得卸载或修改。

## 5. 官方服务架构

### 5.1 组成

复用现有服务边界并生产化：

- `rendezvous`：TLS/WSS、设备在线状态、配对 mailbox、WebRTC 信令、成员事件投递、短期
  TURN 凭据。
- PostgreSQL：短期会话、在线状态、签名成员信封和投递游标；不保存传输内容。
- coturn：仅转发应用层端到端密文，不落盘。
- 监控与告警：健康、错误率、连接建立时间、TURN 使用量和匿名错误类别。

生产环境必须使用固定官方域名、有效公网 TLS 证书、非默认密钥、受限网络、安全组和备份。
数据库不能暴露公网，coturn 不能与数据库共享网络，TURN 使用短期凭据并限制带宽和配额。

### 5.2 数据最小化

服务端允许保存：

- 随机 DeviceID 或其协议所需标识。
- 在线状态和过期时间。
- WebRTC 信令和 ICE 候选的短期信封。
- 带设备签名的成员授权/撤销信封。
- TURN 短期凭据签发记录和匿名用量计数。
- 固定类别的安全、限流和健康事件。

服务端禁止保存或记录：

- 文件内容、文件名、目录结构和接收目录。
- 文件清单明文、传输历史和本地 Finder 路径。
- 设备私钥、应用层会话密钥、配对码原文日志或完整网络载荷。
- 可由错误信息反推出上述内容的原始请求体。

在线状态、配对会话、信令和 TURN 凭据必须采用短 TTL 自动清理。成员事件的保留策略需要支持
离线设备恢复，同时提供用户发起的设备移除和最终清除流程。

### 5.3 可用性与降级

- 协调服务不可用：已启动应用继续运行，Bonjour 局域网直连仍可用。
- TURN 不可用：仍尝试局域网和互联网点对点；失败后提示“暂时无法建立安全连接”。
- PostgreSQL 不可用：服务健康检查失败，不接受会产生半提交状态的新配对。
- 服务恢复：客户端自动重连、刷新可信状态并用原 TransferID 续传。

公开发布前必须具备健康检查、自动重启、证书到期告警、数据库备份与恢复演练、不可变镜像摘要、
服务端回滚步骤和客户端兼容窗口。服务端新版本必须先向后兼容当前公开客户端。

## 6. 错误与文案原则

普通用户只看到“发生了什么”和“现在能做什么”，不看到实现名词：

| 情况 | 用户提示 | 自动处理 |
| --- | --- | --- |
| 官方服务暂时离线 | “互联网连接暂时不可用；同一网络仍可传输” | 后台退避重连 |
| 目标刚刚离线 | “这台 Mac 刚刚离线，请稍后再试” | 保留源文件，不创建任务 |
| 配对码错误或过期 | “配对码无效，请在旧 Mac 重新生成” | 烧毁过期会话 |
| 等待批准超时 | “旧 Mac 没有确认，请重新配对” | 清除双方临时状态 |
| 旧 Mac 拒绝 | “旧 Mac 未允许加入” | 不写入任何信任 |
| 直连失败但中继可用 | 不弹错误 | 自动切到安全中继 |
| 所有网络路径失败 | “暂时无法建立安全连接，请稍后重试” | 任务保持可恢复 |
| 接收目录不可写 | “请选择一个可接收文件的文件夹” | 暂停接收并打开选择器 |
| 磁盘空间不足 | “这台 Mac 空间不足，还需要约 …” | 不发布不完整文件 |
| 文件校验失败 | “文件未能完整接收，正在重试” | 只重传失败分块 |
| 对方版本过旧 | “请在另一台 Mac 更新 Mac 通道” | 不降级到不安全协议 |
| 成员信任冲突 | “设备信息需要重新确认” | 隔离冲突设备，禁止传输 |

诊断详情可以包含稳定错误代码，但复制内容在生成前必须经过敏感字段清理。

## 7. 测试与发布硬门槛

### 7.1 自动化测试

- 单一公共模式启动、服务离线不阻塞启动、重连去重和系统唤醒恢复。
- v1.0.1 设置迁移，证明身份、信任、目录、历史、TransferID 和 ResumeMap 不变。
- Release 运行时不构造或调用任何 Tailscale 客户端、Serve 配置或 mesh listener。
- 配对码五分钟过期、单次使用、错误次数、限流、拒绝、取消和批准超时。
- 新的主机批准状态机、双方原子信任提交、签名/转录篡改和授权重放。
- 多设备成员添加、离线补齐、重复/乱序事件、公钥冲突、撤销和重新加入。
- LAN → Internet → TURN 路由顺序和路径切换时 TransferID/ResumeMap 保持。
- 单文件、多文件、文件夹、Unicode、空文件、同名、磁盘不足和目录权限。
- 网络中断续传、应用重启续传、完整性失败和临时文件不转正。
- 日志和诊断输出的敏感数据反向测试。

### 7.2 服务集成测试

- 两个独立客户端通过真实 rendezvous 完成六位码、旧 Mac 批准和双向信任。
- Bonjour 局域网直连成功。
- 不同模拟 NAT 网络的互联网点对点连接成功。
- 强制阻断 host/srflx 候选后自动使用 TURN relay 成功。
- rendezvous、数据库或 TURN 分别中断后的明确降级和恢复。
- 服务端数据库及日志中不存在文件名、路径、文件内容或设备私钥。
- 限流、过期清理、短期 TURN 凭据、旧凭据拒绝和非开放代理验证。

### 7.3 真实设备验收

候选构建必须在至少两台真实 Mac 上完成，第三台用于多设备验收：

1. 从公开下载地址分别重新下载同一个 DMG。
2. 两台 Mac 均未安装或未运行 Tailscale，不修改网络设置。
3. 一台显示六位码，另一台输入，旧 Mac 点“允许”；重启后信任仍在。
4. 第三台只与其中一台配对，随后三台互相出现在可信设备列表。
5. 验证同一 Wi-Fi、不同 Wi-Fi、手机热点以及家庭/公司网络组合。
6. 强制直连失败，自动通过 TURN 完成传输。
7. 拖放单文件、多文件、文件夹、中文名、同名文件和至少 1 GiB 文件。
8. 传输中断网并恢复，证明只补发缺失分块，最终 SHA-256 与源内容一致。
9. 更改接收目录、磁盘空间不足、对方离线、拒绝接收和版本过旧提示。
10. 移除设备后其现有连接立即失效，重新配对前不能恢复传输。
11. 从已安装 v1.0.1 覆盖升级，核对身份指纹、信任、历史和目录均保留。

### 7.4 分发验收

- App 和内嵌 WebRTC framework 同时包含 arm64 与 x86_64。
- Developer ID 签名、hardened runtime、时间戳、notarization 和 staple 全部通过。
- `spctl` 对 App 和 DMG 均接受；DMG 摘要和准确 Git commit 写入发布清单。
- 在没有 Xcode、没有本地 Gatekeeper 例外的普通账户完成安装启动。
- GitHub `releases/latest` 指向 v1.1.0，公开 DMG 重新下载后的摘要与本地发布产物一致。

只有自动化测试、服务集成、真实设备跨网络传输和公开产物重下载验收全部通过，才能声明
v1.1.0 可用。单元测试通过、未公证构建启动或本机 localhost 演示都不能代替最终验收。

## 8. 实施顺序与发布策略

实施计划应按以下依赖顺序拆分：

1. 固化迁移合同和单一公共运行时，先用测试证明不再依赖 Tailscale。
2. 调整配对状态机和简化 UI，不改变底层已验证的加密 transcript。
3. 增加多设备成员事件同步。
4. 完成设置页、菜单状态和错误文案精简。
5. 部署带生产域名、TLS、PostgreSQL、rendezvous、coturn 和监控的官方服务。
6. 完成模拟网络集成和服务故障演练。
7. 构建 v1.1.0 候选版，进行两/三台真实 Mac 验收。
8. 签名、公证、发布并从公开地址重新验收。

客户端采用分阶段兼容迁移：生产服务先部署兼容版本，v1.1.0 客户端再发布。旧 v1.0.1 在
兼容窗口内仍可使用公共路径，但不会获得新的简化配对流程。个人网络 UI 必须在 v1.1.0
公开发布前移除；确认新版稳定且升级覆盖完成后，再删除源码中已经不可达的兼容残留。
